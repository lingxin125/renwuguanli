01 · EXECUTIVE SUMMARY

项目结论

该项目不是简单增加几类任务页面，而是对微邮付任务管理的组织方式进行重构：任务仍由上级机构按类型产生，但面向客户经理的执行入口改为以商户为中心聚合。

一句话定义

PC 端负责把商户和任务组织、下发并监控；移动端负责按距离发现或领取商户，以商户为单位一次性查看和处理全部任务，并推动目标商户逐步转化为正式商户。

核心改造

从“按任务类型进入多个列表”改为“按商户维度聚合任务”，降低多任务并行时的查找与跳转成本。

业务闭环

机构下发 → 网点承接 → 客户经理领取或接收 → 现场处理 → 审核与完成 → PC 端查看进度。

拓客闭环

目标商户 → 打卡走访 → 意向商户 → 进件或关联 → 正式商户，过程保留来源、归属和转化记录。

02 · WHY

项目背景与改造目标

原有问题

  • 任务按类型拆分，同一商户的补充资料、风控、挂账等任务分散在不同入口。
  • 客户经理线下走访时需要反复返回和切换，无法围绕一个商户连续处理。
  • 新增任务类型往往意味着继续新增入口、列表和导航，扩展成本持续上升。
  • 风控和挂账长期依赖线下通知、人工转发和资料收集，缺少统一状态与过程留痕。
  • 目标商户主要依赖机构导入或客户经理主动录入，商户发现、距离排序和地图能力需要加强。

改造目标

  • 以商户为聚合主体，单次进入即可查看该商户名下全部任务。
  • 保留各任务原有处理逻辑，只调整上层入口、聚合方式和状态呈现。
  • 建立任务池、领取、处理、审核、驳回、重新提交和完成的统一链路。
  • 支持目标商户的导入、附近展示、走访打卡和逐级转化。
  • 为后续新增任务类型预留统一承载框架，减少重复页面建设。
03 · DOMAIN MODEL

业务模型

商户分类

存量商户正式商户

已经在微邮付平台入驻并归属具体网点，任务重点是资料合规、支付通道、存量维护、风险处置和挂账处置。

目标商户意向商户正式商户

尚未成为平台正式商户的潜在对象，通过走访、打卡、信息完善和进件逐步完成转化。

04 · PC

PC端功能全景

PC 端是机构管理侧，核心职责是组织商户数据、产生任务、查看处理进度和保留详情记录，不承担客户经理现场执行。

正式商户任务管理

  • 按商户号、商户名称、任务类型和任务状态筛选。
  • 通过 Excel 批量导入或下发正式商户任务。
  • 查看待领取、待处理、审核中、已驳回、已完成等状态分布。
  • 同时保留按任务类型详情和按商户维度聚合详情两套原型，用于表达改造前后关系。
  • 查看任务下发、领取、处理、审核和完成的全过程。

目标商户任务管理

  • 批量导入目标商户并下发至网点或任务池。
  • 查看目标、意向、正式等转化阶段及地区分布。
  • 查看具体目标商户的走访、打卡和转化进度。
  • 承接地图找商户导出的潜客数据，再导入目标商户列表。
  • 保留早期围栏和区域点选原型，但最新完整 PRD 已将其从当前方案中简化。

地图找商户

  • 接入腾讯地图及 POI 数据。
  • 在地图上绘制区域，获取区域内尚未成为微邮付正式商户的潜客点位。
  • 将潜客数据导出为 Excel，再进入目标商户批量导入流程。
  • 正式商户地图在最新口径中主要用于位置展示。

任务驾驶舱

  • 原型已覆盖商户数量、任务数量、完成率、任务类型分布和地区分布。
  • 包含时间筛选、趋势图、热力图和实时动态等展示能力。
  • 最新完整 PRD 标记为“本期不做”，当前可作为后续规划或汇报演示素材。
05 · MOBILE

移动端功能全景

移动端面向客户经理，以任务接收、商户领取、现场处理、附近商户查找和目标商户转化为主。

任务类型选择

登录或进入任务管理后先选择“存量商户”或“目标商户”，把两类业务对象和处理目标分开。

存量商户任务列表

提供待领取、已领取、进行中、已完成等视图，支持搜索、筛选、排序和列表／地图切换。

商户维度任务详情

进入一个商户即可查看其全部任务，按状态展示待处理、审核中、已驳回和已完成任务。

具体任务处理

进入原有任务处理表单，完成资料上传、原因说明、解决方案选择、结算账户填写和重新提交。

目标商户管理

查看目标、意向、正式三个阶段，支持列表和地图模式、附近排序、目标商户详情及走访记录。

目标商户新增与转化

可通过系统导入数据、地图搜索 POI 或手动录入形成目标商户，并完成打卡、意向转化和正式商户关联。

移动端关键页面关系

STEP 01任务类型选择
选择存量商户或目标商户
STEP 02商户列表／地图
搜索、筛选、距离排序
STEP 03领取或打卡
确定归属并开始处理
STEP 04商户详情
查看全部任务或转化信息
STEP 05处理与提交
审核、驳回重提或完成转化
06 · END-TO-END FLOW

核心业务流程

正式商户任务

01机构下发
按任务类型导入或创建任务
02聚合到商户
同一商户的任务集中展示
03客户经理领取
领取商户及其全部任务
04逐项处理
进入对应任务表单提交
05审核闭环
完成或驳回后重新提交

目标商户转化

01形成目标商户
系统导入、地图搜索或手动录入
02附近发现
按客户经理当前位置排序
03走访打卡
补充照片、联系人和纪要
04意向转化
持续跟进并完善资料
05正式商户
进件成功或关联正式商户号

地图能力的定位

地图不是独立业务终点，而是服务于“发现附近商户、展示商户位置、辅助筛选导航、获取目标商户数据”的工具层。

07 · RULES

业务规则与状态流转

规则主题当前方案结论
领取粒度存量任务的领取概念上升到商户维度；领取商户后，该商户下全部任务归属当前客户经理。
领取时效领取后 3 天内至少处理 1 个任务；到期前 1 天提醒，逾期失效并需要重新领取。
任务状态待处理 → 审核中 → 已完成；审核不通过时进入已驳回，再由客户经理修改后重新提交。
完成商户商户下全部任务完成后，从“进行中”进入“已完成”；移动端原 PRD 建议保留近 90 天记录。
特殊排序即将失效优先于驳回任务，驳回任务优先于普通进行中任务，随后再按距离等条件排序。
目标商户状态目标商户 → 意向商户 → 正式商户；也可在核实后直接输入正式商户号完成关联。
位置能力商户列表可以按照客户经理当前距离展示，地图模式支持点位、卡片、列表联动和导航。
权限与归属任务最终下发到网点并由客户经理执行；目标商户的可见范围应结合来源、归属及转化状态控制。

原型不是统一技术应用

页面均为独立 HTML，依赖 Tailwind CDN 和页面内脚本，没有统一路由、数据层或组件体系。它适合方案演示和交互验证，不能直接等同于生产实现。

项目经历多轮调整，部分早期方案仍保留在文档和原型中。建议以“最新完整 PRD 的明确更新说明”为当前主口径，旧文档用于理解演进过程。

主题当前推荐口径历史或原型表现
地图下发方式 当前 最新完整 PRD v6.0 明确简化地图功能，取消围栏拓客和区域点选指派。 历史 早期目标商户地图方案仍详细描述网点围栏、市级区域点选和任务池领取。

任务驾驶舱 当前 最新完整 PRD 标记为本期不做。 原型 页面和 README 已完整展示统计、图表、热力图和动态信息。

10 · NEXT

风险与后续建议

当前可见风险

  1. 历史方案混用：若不先冻结地图口径，后续功能增加容易重新引入已取消的围栏与区域指派。
  2. 归属规则不够统一：存量商户领取规则较清晰，目标商户的领取、打卡和可见范围仍需统一。
  3. 原型链接缺口：挂帐任务明细页.html 引用了不存在的 任务列表页.html。
  4. 开发工具资源缺口：升级版地图页面引用了不存在的 js/stagewise-toolbar.js。
  5. 外部资源依赖：移动页面普遍使用 Tailwind CDN，离线或受限网络下可能无法正确显示。
  6. 静态数据一致性：驾驶舱、列表和详情中的统计数字是演示数据，尚未形成统一数据源。

增加功能前的建议

  1. 先确定本期范围：地图仅做展示／找商户，还是重新启用机构地图下发。
  2. 统一两类商户的“任务池、归属、领取、失效、重新领取”规则。
  3. 补充统一状态字典，明确商户状态、任务状态和审核状态之间的关系。
  4. 以商户任务详情作为新增任务类型的统一容器，具体任务继续使用独立处理表单。
  5. 为目标商户定义来源字段、来源展示名称、可见范围和转化后的数据继承规则。
  6. 将原型导航关系整理成统一页面地图，避免后续新增页面继续产生断链。

本次分析未擅自处理的内容

失效链接、历史地图功能、原型业务文案和页面内部交互均未修改。本次移动端改造仅增加统一手机／小程序展示外层，保持原功能界面与业务逻辑不变。
